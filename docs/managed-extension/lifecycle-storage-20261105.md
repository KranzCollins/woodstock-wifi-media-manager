# Lifecycle storage: schema and transaction usage, 5 November 2026

Status at 17:54 UTC: the additive schema validates and its Prisma client was generated. The media-capability service, Prisma store and private-storage adapter passed a disposable PostgreSQL 18.4 integration test with actual PNG sniffing, bytes, concurrent quota claims and retained revocation. Dispatch authority and budget in that targeted test are explicit fakes. The organization-scoped lifecycle repository now passes actual PostgreSQL18.4 concurrent feed/key/CAS, rollback and tenant checks. Business service/dispatcher integration, baseline regeneration and full call race/crash tests remain pending. **The schema alone proves no durability or at-most-once property.** Every guarantee below holds only if the repository/service follow the transaction rules in this document, and only once actual PostgreSQL race and crash tests show it.

Authority: `lifecycle-root-decisions-20261105.md` and `lifecycle-architecture-corrections-20261105.md`. Where `lifecycle-implementation-20261105.md` §3 differs (columns on `ManagedPost`/`ManagedOperation`, lifecycle kinds in `ManagedChangeEvent`, unbounded repeats, read-only polls without state), this document supersedes it. `managed.lifecycle.contracts.ts` is still being reconciled. This schema follows the corrections, not that file's current state (see §9).

Nothing here activates anything. There is no seed, grant, DB switch or background job. A schema default never makes a row admitted, active or enabled:

- `ManagedSchedule.status` and `ManagedDispatchCall.status` have no default.
- `ManagedDispatch.status` defaults to `PENDING`, which means not admitted.
- `ManagedPostLifecycle` defaults to `DRAFT` at generation 0.

Gates stay in configuration, as in the root decisions, and are empty/off.

## 1. Models

All eight models are new. No existing model or column changes. Every table has `organizationId`, and no row is ever deleted.

### `ManagedLifecycleOrganization`

The lifecycle feed's own dense counter (`sequence`). It is created lazily by the organization's first lifecycle write, never by a seed or migration. It is never touched without `ManagedOrganization` being locked first (§2). `ManagedOrganization.sequence` is never advanced by a lifecycle write.

### `ManagedPostLifecycle`

- **Key.** `managedPostId` is `@unique`. Every read also filters on `organizationId` (`findFirst({ where: { managedPostId, organizationId } })`, as `getManagedPost` does).
- **Defaults.** No row means `DRAFT`, generation 0, no schedule. Existing posts need no backfill.
- **Fields:**
  - `lifecycle`: `DRAFT | SCHEDULED | DISPATCHING | PUBLISHED | FAILED | REVIEW | DELETED`
  - `scheduleGeneration`
  - `activeScheduleId`
  - `version`, +1 on every change
  - `lastLifecycleSequence`
  - `lastOperationKey`
- **`activeScheduleId`** is the single pointer to the post's ACTIVE or ENDING schedule. It is `@unique`, so no schedule can be active for two posts. "At most one live schedule per post" is enforced by this one column, because Prisma cannot express a partial unique index.
- **Retained soft-delete markers.** `deletedAt`, `deletedOperationKey`, `deletedSequence` and `deletedFromLifecycle` are set once and never cleared.

### `ManagedLifecycleOperation`

The immutable acknowledged answer of one lifecycle write:

- `operationKey`, `kind`, `payloadHash`, `credentialId`
- `managedPostId`, plus `dispatchId` for RESOLVE and `scheduleId` for the schedule created or ended
- `revision` (bound)
- `scheduleGeneration` (after the write)
- `sequence` (the lifecycle sequence of the event that carries this key)
- `result` (the exact JSON first answered, with `replayed: false`)
- `committedAt` (written by the service, equal to `result.committedAt`, not a DB default)

Uniques are `(organizationId, operationKey)` and `(organizationId, sequence)`. The repository exposes create and get only. There is no update.

### `ManagedLifecycleChangeEvent`

The separate lifecycle feed. Its uniques and indexes:

- `(organizationId, sequence)` is unique.
- `(organizationId, managedPostId, sequence)` is indexed for ordered per-post history. Prisma validation passed; index names are generated by Prisma.

`data` is the contract's public projection only (the schedule, dispatch and lifecycle views). It never holds:

- a credential id
- a holder or fencing token
- a request hash or sent ledger
- a pending envelope
- the release snapshot
- a storage key or a capability

### `ManagedSchedule`

Fixed at acceptance:

- `scheduleGeneration`, `mode` (`AT | NOW`), `revision`, `bindingGeneration`
- `integrationId`, `providerIdentifier`, `identityFingerprint`
- `contentSha256` (W&W's approved digest) and `releaseHash` with `releaseHashVersion` (the owned hash)
- `codec`
- `release`: the server-private decoded reviewed release. It holds the decoded text, delays, media pins (`mediaId`, `evidenceId`, `sha256`, `byteLength`, `mimeType`, the options W&W reviewed) and the settings. It holds no token, credential, storage key, path or URL.
- `anchorAt`, `intervalDays`, `maxOccurrences` (finite: 1 for once, at most 7), `maxLatenessMs`
- the captured window `policyGrantedAt` / `policyExpiresAt` (exclusive)
- the creating `operationKey` and `credentialId`

Mutable:

- `status`
- `version`
- `lastOccurrence`, which starts at `maxOccurrences - 1` and is only ever lowered
- `endRequestedOperationKey` / `endRequestedAt`
- the terminal markers `endedAt`, `endedCode`, `endedOperationKey`

Constraints:

- `(managedPostId, scheduleGeneration)` is unique. Generations only grow, so each generation has at most one schedule.
- `(organizationId, operationKey)` is unique: one schedule per creating key.
- `(organizationId, status)` is indexed.

### `ManagedDispatch`

One occurrence of a schedule.

- **Timing and status:** `occurrence`, `dueAt`, `admissibleUntil` (`dueAt + maxLatenessMs`), `status`, `version`, `code`.
- **Binding, fixed at materialization:** `revision`, `bindingGeneration` and `scheduleGeneration`, with both hashes (`contentSha256`, `releaseHash`).
- **Public projections:** `members` (`[{ position, postId, status, code, release }]`) and `resolution`.
- **Cancellation:** `cancelledByOperationKey`.
- **Lease:** `leaseHolder`, `leaseExpiresAt` and `fencingToken` (+1 on every lease claim, never on a renewal).
- **`activeCallId`** (`@unique`): the single call admitted and not yet settled, whether DISPATCHING or PENDING_PROVIDER.
- **Continuation:** `nextActionAt`, `nextStep`, `nextMember`.
- **Deferral:** `deferralCode`, `deferralCount`, `firstDeferredAt`, `lastDeferredAt`.
- **Settlement and feed:** `admittedAt`, `settledAt`, `lastLifecycleSequence`.

Constraints:

- `(scheduleId, occurrence)` is unique, so an occurrence can never be materialized twice.
- `(organizationId, status, nextActionAt)` is the dispatcher's due scan.
- `(organizationId, managedPostId)` is indexed.

`version` is the public `dispatchVersion`. It moves +1 on each status or member transition, and never on a lease claim or renewal, so W&W's bound `expectedDispatchVersion` does not go stale while a dispatch sits on a delay or a poll.

`nextActionAt` is the one "look at me next" time:

- `dueAt` at materialization
- a deferral's next attempt
- a member delay
- the next poll

### `ManagedDispatchCall`

The durable pre-IO admission of one provider mutation.

- **Identity:** `member`, `postId`, `step` (`POST | COMMENT | FINALIZE`), `attempt` (1, or 2 only after a proved NOT_SENT).
- **Outcome:** `status`, `code`.
- **Fencing:** `holder`, `dispatchVersion` (the dispatch version at admission), `fencingToken` (the dispatch's token at admission).
- **Timing:** `leaseExpiresAt`, `deadlineAt`.
- **Request:** `requestHash`, the hash of the exact adapter input. It excludes tokens and capability URLs.
- **Budget:** `reservedUnits`, `consumedUnits`, `pollReservedUnits`.
- **Private continuation:** `sentLedger` (the transport's own record of which sub-requests started and how far each got) and `pendingEnvelope` (the provider continuation needed to resume read-only polling).
- **Polling:** `pollCount`, `nextPollAt`, `pollDeadlineAt`, `lastPolledAt`.
- **Settlement:** `result` (`{ releaseId, releaseURL }` only), `admittedAt`, `settledAt`.

Constraints:

- `(dispatchId, member, step, attempt)` is unique.
- `(organizationId, status)` and `(organizationId, dispatchId)` are indexed.

Polls of a PENDING_PROVIDER call are counted on that call and are not new rows.

### `ManagedMediaCapability`

`ManagedMediaCapabilityRecord`, field for field. `capabilityIdSha256` is the primary key, and the store's `get`/`claimFetch`/`revoke` address rows by it. There is no extra column, so a `select` of the record fields maps 1:1.

Constraints:

- `(organizationId, callId, evidenceId)` is unique. This is the store's documented "null when a capability exists for the same organization, call and evidence".
- `(organizationId, callId, mediaId)` is unique: `mediaId` is unique per call and deliberately not globally.

There is no further index, because `revokeCall(organizationId, callId)` uses the prefix of either unique.

## 2. Lock order (every lifecycle mutation)

Every transaction that writes any lifecycle row runs with the default isolation, like `ManagedRepository.mutate`. Under READ COMMITTED, each statement after the lock sees everything committed by the previous holder. It takes rows in this order:

1. **`ManagedOrganization`**, with exactly the existing no-op lock: `tx.managedOrganization.update({ where: { organizationId }, data: { updatedAt: new Date() }, select: { sequence: true } })`. A lifecycle write never creates this row; a missing row is a refusal (P2025 → NOT_FOUND). The DRAFT `sequence` it returns is read only, never written.
2. **`ManagedLifecycleOrganization`**, only if the transaction appends lifecycle events. It is read with `findUnique`, created if absent, and its `sequence` is set to the last allocated value at the end, mirroring `mutate`. Lock 1 makes the lazy create race-free among managed writers. A P2002 here means some writer skipped lock 1. The transaction then aborts and nothing is written.
3. **Lifecycle rows**, in this order: `ManagedPostLifecycle` → `ManagedSchedule` → `ManagedDispatch` → `ManagedDispatchCall` → `ManagedMediaCapability`.
4. **The post's group**: `Post` rows, then `ManagedPost`.

DRAFT writes (`mutate`) and connection writes take lock 1 first and never touch lifecycle rows, so there is no cycle. No transaction holds a lock across network IO. Pinned media reads, codec decoding, release recomputation, Redis budget reservations and provider calls all happen outside the transaction, and their results are rechecked inside it.

Transaction options are those of `mutate` (`{ maxWait: 10000, timeout: 20000 }`). Reads use `$transaction(..., { isolationLevel: RepeatableRead })` like `ManagedRepository.read`. They are the feed, the operation lookup, the post lifecycle and dispatch views, and the capability authority's `activeCall`. Reads take no locks.

The one deviation, for root to accept or reject, is the media-capability fetch path. `ManagedMediaCapabilityStore` documents each method as one statement. `claimFetch` and the single `revoke` called from a provider's fetch are single-row conditional writes on `ManagedMediaCapability`. They don't read or write any DRAFT or lifecycle-state row and don't allocate a sequence. This document leaves them without lock 1, because taking it would make a provider's media fetch wait behind DRAFT transactions of up to 20 s. `create` (mint) and `revokeCall` are issued by the dispatcher. `revokeCall` on settle runs inside the settle transaction, under locks 1-3. If root requires lock 1 literally everywhere, the store wraps each of these statements in a transaction that first takes lock 1. Atomicity is unchanged.

## 3. Operation keys: one namespace shared with drafts

`ManagedOperation`'s `(organizationId, operationKey)` unique is the single claim for both DRAFT and lifecycle keys. A lifecycle write inserts, in the same transaction as its effects:

- `ManagedOperation { operationKey, kind, payloadHash, managedPostId, revision, sequence: 0, credentialId }`, where:
  - `kind` is the lifecycle kind (`SCHEDULE | PUBLISH_NOW | CANCEL | DELETE | RESOLVE`)
  - `revision` is the bound revision (for RESOLVE, the dispatch's revision)
  - `sequence: 0` means *no DRAFT feed position*. DRAFT sequences start at 1, so 0 never collides.
- `ManagedLifecycleOperation` with the stored result and the lifecycle `sequence`

No `ManagedChangeEvent` is appended and `ManagedOrganization.sequence` does not move. This is a new value domain in two existing columns (`kind` values outside `CREATE_DRAFT`/`EDIT_DRAFT`, and `sequence = 0`). It applies to new rows only, and historical rows are untouched. Root must accept it (§9).

The lifecycle write path runs after locks 1-2, before any gate:

- **No `ManagedOperation` row for the key:** run the gates. A refusal writes no claim, so the key stays ABSENT and reusable, which is the existing DRAFT semantics. On success, insert both rows plus the effects and events.
- **A row with a DRAFT kind:** `409 OPERATION_KEY_KIND_MISMATCH`.
- **A row with a lifecycle kind:** read `ManagedLifecycleOperation` by the same key.
  - another credential: `OPERATION_KEY_CREDENTIAL_MISMATCH`
  - another kind: `OPERATION_KEY_KIND_MISMATCH`
  - another `payloadHash`: `OPERATION_KEY_PAYLOAD_MISMATCH`
  - otherwise: answer the stored `result` with only `replayed` set to `true`. No other write and no sequence.
  - A lifecycle `ManagedOperation` row without its `ManagedLifecycleOperation` row is impossible, because they commit together. If it ever appears it is answered as an internal refusal, never as ABSENT and never by sending anything.

The unique on `ManagedOperation` is also the database backstop. Two writers that both skipped lock 1 still cannot both commit the key.

`GET /managed/v1/lifecycle/operations/:operationKey` is a RepeatableRead read. `asOfSequence` is `ManagedLifecycleOrganization.sequence`, or 0 when the row is absent.

- no claim: ABSENT
- a DRAFT kind: typed409 OPERATION_KEY_KIND_MISMATCH
- a lifecycle kind: COMMITTED, from `ManagedLifecycleOperation`. `ack` compares its `scheduleGeneration` with the current `ManagedPostLifecycle.scheduleGeneration`.

The existing DRAFT consumers must change before the first lifecycle claim exists. Today they read `ManagedOperation` without looking at `kind`:

- **`ManagedService.operationStatus`** (`GET /managed/v1/operations/:key`) would answer `COMMITTED` with a DRAFT revision snapshot for a lifecycle key, because the bound revision exists. Root's decision is a typed `409` kind mismatch there. That is a code change in `managed.service.ts`, outside this job.
- **`ManagedService.replay`** (DRAFT create/edit) already refuses a lifecycle key with `OPERATION_KEY_PAYLOAD_MISMATCH`, because a lifecycle payload hash includes its kind and cannot equal a draft hash. The new lifecycle kind check returns typed409 OPERATION_KEY_KIND_MISMATCH. Existing CREATE_DRAFT versus EDIT_DRAFT mismatches retain their original payload-conflict semantics.

With lifecycle gates off, no lifecycle claim is ever written, so DRAFT behavior is unchanged until both checks land.

## 4. Post rows and `ManagedPost`

These authorized changes to actual `Post` rows are each made inside a lifecycle transaction:

- `state` (`DRAFT ↔ QUEUE`, `→ PUBLISHED` with `releaseId`/`releaseURL`, `→ ERROR`)
- `publishDate`
- retained `deletedAt`

In that same transaction, `ManagedPost.rowFingerprint` is recomputed from the rows as written, with the existing `rowFingerprint()`. Nothing else on `ManagedPost` changes: `revision`, `bindingGeneration`, `lastSequence` and `lastOperationKey` keep their DRAFT meaning. No `ManagedPostRevision` row is written or rewritten. A transition without a Post row change (for example a dispatch deferral) does not touch `rowFingerprint`. The legacy reader's `integrity` therefore stays `CONSISTENT` across authorized transitions, and still reports `DRIFTED` for foreign writes. What the legacy v2 reader answers for a soft-deleted group is not solved by this schema (§9).

## 5. Transaction shapes

All of these follow §2. Every dispatch transition sets `version + 1`, updates `members`, appends one event with the next lifecycle sequence and sets `lastLifecycleSequence`. One event per entity transition keeps the feed dense: a transaction may append several events, and each takes the next sequence.

**Schedule / publish-now.**

1. Recheck revision, binding, release hash and codec against the pinned reads.
2. `ManagedPostLifecycle`: generation +1, `SCHEDULED`, `activeScheduleId`.
3. `ManagedSchedule` `ACTIVE` with the captured window, `lastOccurrence = maxOccurrences - 1`.
4. Dispatch 0 `PENDING`, with `nextActionAt = dueAt` and both hashes.
5. Rows `DRAFT → QUEUE` plus `rowFingerprint`.
6. The claim and the operation.

Publish-now refuses while `activeScheduleId` is set.

**Cancel.** Refused while an affected occurrence's dispatch is ADMITTED or has an `activeCallId`, and while any dispatch of the post is UNKNOWN or PARTIAL.

- **OCCURRENCE `n`:**
  - Dispatch `n` at the expected version becomes `CANCELLED`, with `cancelledByOperationKey`.
  - The generation is unchanged.
  - If `n < lastOccurrence`, occurrence `n + 1` is materialized at `anchorAt + (n + 1)·intervalDays`, with the schedule's own generation. An explicitly CANCELLED predecessor is sufficient.
- **REMAINING `from f`:**
  - A materialized PENDING dispatch at occurrence `≥ f` becomes `CANCELLED`. Earlier PENDING or admitted occurrences remain unchanged; unmaterialized occurrences before `f` remain eligible under the original window.
  - `lastOccurrence = f - 1`, and `endRequestedOperationKey` / `endRequestedAt` are set.
  - The post and dispatch generations remain unchanged; the schedule version advances.
  - If an earlier occurrence is still admitted, the schedule becomes `ENDING`. That dispatch keeps and settles under its own `scheduleGeneration`. Its later steps use its own fixed generation and admission, never the post's new generation. Then the schedule moves to `CANCELLED`.
  - Otherwise the schedule is `CANCELLED` now, and `activeScheduleId` is cleared.
- **SERIES:** refused while any occurrence is admitted. PENDING becomes `CANCELLED`, the schedule version advances (generation unchanged) and the schedule is `CANCELLED`.

**Delete (retained soft delete).**

- Refused while any dispatch of the post is ADMITTED, UNKNOWN or PARTIAL.
- PENDING dispatches become `CANCELLED`, and the schedule becomes `SUPERSEDED_BY_DELETE`.
- The generation advances.
- `ManagedPostLifecycle` gets `DELETED`, the deleted markers and `activeScheduleId = null`.
- Rows get `deletedAt` (kept) plus `rowFingerprint`.
- The social-network post is never touched.

**Resolve.**

- Applies only to an UNKNOWN/PARTIAL dispatch at the expected version.
- The dispatch becomes `RESOLVED_*` with the public `resolution`. Call rows stay as they are; they are history.
- Nothing is sent.

**Admission.** Outside the transaction:

- the Redis lease is held
- the adapter's declared maximum units for the step are reserved in the shared bucket; none available means a deferral
- the pinned media reads
- the release decoded from `ManagedSchedule.release`, rehashed to `releaseHash`

Inside the transaction:

- recheck the gates
- the dispatch's `dueAt < policyExpiresAt` (captured)
- the dispatch is not past `admissibleUntil`

Then:

- **Lease:** `leaseHolder = me`, `fencingToken + 1`, `leaseExpiresAt` set.
- **Dispatch:** `PENDING → ADMITTED` with `admittedAt`.
- **Call:** inserted `DISPATCHING` with `holder`, `dispatchVersion` (the new version), `fencingToken`, `leaseExpiresAt`, `deadlineAt`, `reservedUnits` and `requestHash`. `activeCallId` points at it.
- **Commit.** Only after the commit may the transport start.

A failed gate is a recorded `NOT_SENT` with its code. A budget refusal or an organization already in flight is a deferral: `deferralCode`, `deferralCount + 1`, `firstDeferredAt`/`lastDeferredAt` and `nextActionAt` = the next attempt. The status stays PENDING, and the version is unchanged because nothing public changed.

**Immediately before each outgoing mutation.** In a short transaction:

1. Take lock 1.
2. Run `managedDispatchCall.updateMany({ where: { id, organizationId, status: 'DISPATCHING', holder, fencingToken, dispatchVersion, leaseExpiresAt: { gte: now + deadline } }, data: { updatedAt: now } })` and require `count === 1`.
3. Read the dispatch and require `leaseHolder`, `fencingToken` and `version` to equal the call's.

Commit, then send. Lease renewals happen at step boundaries (each new call admission and each poll), not by relying on one long lease. Recovery only reclaims `leaseExpiresAt < now`, so it cannot reclaim a live admission.

**Settle.** Takes locks 1-3 and is conditional on the call still being `DISPATCHING` (or `PENDING_PROVIDER` for a poll answer), with the same `holder` and `fencingToken`, and `dispatch.version === call.dispatchVersion`.

- The call gets its outcome, `sentLedger`, `consumedUnits`, `result`/`code` and `settledAt`. A pending answer instead gets `pendingEnvelope`, `pollDeadlineAt` and `nextPollAt`.
- The dispatch members and status move. `activeCallId` is cleared once the call is terminal, and the next step goes into `nextActionAt`/`nextStep`/`nextMember`.
- The call's capabilities are revoked (`CALL_SETTLED`).
- The Post rows and `rowFingerprint` are updated.
- `ManagedPostLifecycle` is updated.
- The schedule materializes the next occurrence or ends.

A stale settle never adopts the answer or clears UNKNOWN. The root storage amendment requires retaining sanitized late evidence for human review; that implementation is still pending.

**Poll** (read-only at the provider). Before IO, reserve the poll units and take locks 1-3:

- check the call is `PENDING_PROVIDER` under the current lease and `pollDeadlineAt` is not passed
- set `pollCount + 1`, `pollReservedUnits + units` and `lastPolledAt`
- set the next `nextPollAt` with exponential backoff, mirrored into `dispatch.nextActionAt`
- renew the lease

Budget exhaustion defers the poll without losing it. Passing `pollDeadlineAt` gives `UNKNOWN PENDING_UNCONFIRMED`.

**Recovery** (lease expired). Takes locks 1-3 and reclaims with `leaseHolder = me` and `fencingToken + 1`:

- **A `DISPATCHING` call:** the call becomes `UNKNOWN` (`DISPATCHER_LOST`/`LEASE_LOST`) and is never resent. The dispatch becomes `UNKNOWN`, or `PARTIAL` if a member was published. Capabilities are revoked (`CALL_INACTIVE`).
- **A `PENDING_PROVIDER` call:** it takes the new holder and token and resumes polling at `nextPollAt` with its `pollCount`.
- **No call in flight:** the persisted delay resumes. A new step is a new admission.

**Feed read.**

- `head` is the lifecycle counter.
- Events are those with `sequence > cursor`, up to `head`, in order.
- Writers are serialized by lock 1 and commit the counter with their events, so a RepeatableRead snapshot never sees a gap.

## 6. Uniqueness and cross-organization validation

The repository pattern is kept: there are no foreign-key relations.

- Every repository method is opened for one organization, like `PrismaManagedStore`, and puts `organizationId` in every `where`, including lookups by a globally unique id.
- Any reference written into a row (`scheduleId`, `dispatchId`, `callId`, `managedPostId`, `integrationId`, `evidenceId`) is copied from a row read in the same transaction under the same `organizationId`, never from request input alone.
- A row of another organization is therefore NOT_FOUND.

The uniques are what the database can guarantee by itself, even against a writer that breaks these rules:

- each key claimed once
- each operation and event sequence used once
- each occurrence materialized once
- each call attempt recorded once
- at most one live schedule per post and one unsettled call per dispatch, through the single `@unique` pointers
- one capability per call and evidence/media

Whatever needs a partial index, a CHECK or a comparison across columns is enforced by the service under lock 1, not by the schema. That includes:

- version and generation monotonicity
- the 7-day / `2026-11-10T23:00:00.000Z` bound
- `lastOccurrence ≤ maxOccurrences - 1`
- `fetchCount ≤ maxFetches`

`claimFetch` is `updateMany({ where: { capabilityIdSha256, fetchCount: expected, revokedAt: null, expiresAt: { gt: now } }, data: { fetchCount: expected + 1 } })` and returns `count === 1`. `maxFetches` is immutable and the service checks `expected < maxFetches` first, so the count can never exceed it. `create` maps P2002 on the id or on either unique to `null`.

## 7. Budget units recorded

1 unit = 1 outbound request, as in the existing shared 200/hour per-organization bucket. The bucket itself is Redis, and this schema only records the units:

- **A lifecycle API request** is metered by the existing throttler. It is not recorded here.
- **A call** has `reservedUnits`, the adapter's declared maximum for the step, reserved before admission. It also has `consumedUnits`, the sub-requests the transport actually started. A request beyond `reservedUnits` after any sent sub-request is UNKNOWN. Unused units are not returned.
- **Polls** reserve separately (`pollReservedUnits`).
- **Media fetches** cost 1 unit each (`budgetUnitsPerFetch`) and are counted by the capability's `fetchCount`.

The provider IO attributable to one call is therefore `consumedUnits` + poll units + its capabilities' `fetchCount`.

## 8. Capability authority mapping

`ManagedMediaCallAuthority.activeCall(org, callId)` is a RepeatableRead read of the call and its dispatch, both under `org`:

- `active`: the call is `DISPATCHING` with `holder`/`fencingToken` equal to the dispatch's, or the call is `PENDING_PROVIDER`.
- `activeUntil`: the earlier of `leaseExpiresAt` and `pollDeadlineAt` (when pending), and the captured `policyExpiresAt`.
- `dispatchVersion`: `call.dispatchVersion`.
- `media`: the pins of `call.member` in `ManagedSchedule.release`.

If the same media is referenced twice in one call, the dispatcher reuses the one grant. A second mint is `ALREADY_MINTED` under either unique.

## 9. Not proved, and open consistency issues

- **Not proved.** Durability, at-most-once and lock behavior are unproved until root generates the client, writes the additive migration, regenerates the baseline and its SHA256, and runs actual PostgreSQL two-process races and SIGKILL recovery. `fake.prisma.db.ts` also needs the eight models before any unit spec can use them.
- **DRAFT operation consumers** (`operationStatus`, `replay`) need the `kind` gate of §3 before any lifecycle claim is written.
- **`ManagedOperation` value domain.** `kind` gains lifecycle values, and lifecycle claims carry `sequence = 0`. These are new values in existing columns, for new rows only. Root must accept them, or choose another rule, before code depends on them.
- **Lock-1 exemption.** The media-capability fetch path deviates from "every mutation locks `ManagedOrganization`" (§2). This needs root's decision.
- **Contracts drift.** The current `managed.lifecycle.contracts.ts` differs from the corrections in four places:
  - Requests and views have no `contentSha256`.
  - `MANAGED_LIFECYCLE_EVENT_KINDS` is described as new `ManagedChangeEvent` kinds, where the corrections call for a separate feed.
  - Polling is a fixed 20 s × 90 instead of backoff to a deadline.
  - Repeat materialization is `NEXT_AFTER_PREVIOUS_PUBLISHED`, where the corrections also allow RESOLVED_PUBLISHED or CANCELLED.

  The schema stores what the corrections require. `endsAfterOccurrence` in the schedule view projects as `lastOccurrence` when `endRequestedOperationKey` is set.
- **`contentSha256`** is stored as W&W confirmed it. Whether the owned side can recompute it independently depends on the reconciled contract. Until then the owned side verifies only `releaseHash`.
- **`(organizationId, callId, mediaId)`** is stricter than the store's documented `(org, call, evidence)` condition. It refuses (fail closed) if one call ever pinned two evidence ids of one media.
- **Clocks.** Lease and expiry comparisons use application time, because there is no raw SQL and so no DB `now()`. Skew between processes must be bounded operationally. A sender paused after its pre-IO check can still send once. That send ends as a durable UNKNOWN, never as a second automatic send, so there is no exactly-once claim.
- **Soft-deleted groups.** What the legacy v2 reader and the DRAFT feed answer for a soft-deleted group (DELETED is not in the v2 decoder) is root's tombstone/projection decision. The schema only retains the rows.
- **Late answers.** A late provider answer from a stale holder is not recorded anywhere. If root wants it as resolution evidence, that is a new nullable column later.
